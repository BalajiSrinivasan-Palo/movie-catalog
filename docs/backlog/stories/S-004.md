## Objective

Walking skeleton: frontend to gateway to both services.

## Acceptance criteria

- `S-004.AC1`: GraphQL `health`-style query reaches the gateway and calls `grpc.health.v1` on both services; the shell footer shows their status. (D23: it stays quiet while checking and when every service is up, and shows a warning only when a service is down or the gateway is unreachable.)
- `S-004.AC2`: Gateway generates/accepts `X-Correlation-Id` and forwards it as gRPC metadata; services log it in MDC.
- `S-004.AC3`: A `DataFetcherExceptionResolver` maps gRPC `Status` plus `ErrorDetail` to GraphQL codes per ADR-005 (table-driven contract test for every row).
- `S-004.AC4`: gRPC calls use deadlines; a stopped service yields `UNAVAILABLE` within the deadline, not a hang.
- `S-004.AC5`: CORS restricted to `FRONTEND_ORIGIN`; security headers set; GraphQL depth/complexity limits and dev-only introspection configured.
- `S-004.AC6`: `scripts/dev.sh` starts the three services and the Vite dev server with configurable ports and data directories; `scripts/dev.sh --check` waits for health of all four and exits non-zero on timeout.
- `S-004.AC7`: A gateway-generated field error (for example `credit.person.not_found`) is returned as `VALIDATION_FAILED` with `fieldErrors[{field, messageKey}]`; malformed ids return `VALIDATION_FAILED` with key `id.invalid`; both have mapping tests.
- `S-004.AC8`: Schema has `health: [ServiceHealth!]!` returning one entry per backend (`service`, `status`, `detail`), used by the footer; gRPC servers register `grpc.health.v1`; gRPC max inbound message size is configured (NFR-SEC-06) and tested.

## Business rules and edge cases

- No internal details in error messages (NFR-UX-06).

## Test expectations

- GraphQL contract tests for the error mapping.
- In-process gRPC integration test.
- Fault-injection test: downstream stopped.
