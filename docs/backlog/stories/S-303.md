# S-303: Gateway multipart upload and artwork GET endpoints

**Epic:** E03 Artwork  
**Priority:** Must · **Size:** M · **Order:** 16 · **Wave:** 6  
**Status:** Draft (Phase 4)  
**Depends on:** S-301, S-302, S-004  
**Requirements:** FR-ART-01, NFR-ARCH-03, NFR-ARCH-05, NFR-SEC-02, NFR-TEST-03  
**BRD acceptance criteria owned:** none

## Objective

Gateway multipart upload and artwork GET endpoints.

## Acceptance criteria

- `S-303.AC1`: `uploadArtwork` accepts a GraphQL multipart request (operations, map, file), validates structure and size, and streams to movie-service in 64 KiB chunks; the file is never fully buffered.
- `S-303.AC2`: Client abort cancels the gRPC call (verified by a test observing cancellation in movie-service).
- `S-303.AC3`: `GET /artwork/{movieId}/{thumbnail|original}?v=` streams from `DownloadArtwork` with `Content-Type`, `ETag`, immutable `Cache-Control`, `nosniff`; 404 for unknown movie/artwork; invalid ids rejected.
- `S-303.AC4`: Malformed multipart (missing `map`, wrong part names, oversize) returns the standard GraphQL error shape.
- `S-303.AC5`: Multipart streaming: Spring's multipart resolver is disabled for `/graphql`; the file part is read with `Part.getInputStream()` and forwarded in chunks; a test with `-Xmx128m` and a 5 MiB upload proves it is not buffered in memory.
- `S-303.AC6`: `GET` handles `If-None-Match` with 304; a wrong or missing `v` still serves the current artwork (the token only busts caches); after upload the gateway returns the movie via `GetMovie`.

## Test expectations

- Unit: multipart parser negatives.
- Integration: upload then GET round trip; cancel propagation.
- Contract: GraphQL error shapes; headers on GET.
