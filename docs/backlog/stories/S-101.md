# S-101: Create person

**Epic:** E01 People management  
**Priority:** Must · **Size:** M · **Order:** 5 · **Wave:** 3  
**Status:** Draft (Phase 4)  
**Depends on:** S-004  
**Requirements:** FR-PPL-02, NFR-SEC-01, NFR-REL-04  
**BRD acceptance criteria owned:** AC-FR-PPL-02-2

## Objective

Create person.

## Acceptance criteria

- `AC-FR-PPL-02-2`: as defined in `docs/requirements/BRD.md` section 10.
- `S-101.AC1`: `PeopleService.CreatePerson`, Liquibase changeset for `person`, gateway `createPerson`, and `/people/new` form are implemented.
- `S-101.AC2`: Field errors from the server render under the matching input; form input is kept.
- `S-101.AC3`: `AC-FR-PPL-02-1` (person appears in the list) is verified in S-102, which owns it; here the created person is verified through `person(id)`.
- `S-101.AC4`: On success the UI shows a toast and navigates to `/people`.

## Business rules and edge cases

- BRD s7: name 1–200 trimmed; birth date not future and not before 1850-01-01; bio ≤ 2000.
- Names are not unique.
- Invalid calendar dates (for example 30 Feb) are rejected; 'not in the future' is evaluated in UTC; length is counted in Unicode code points.

## Test expectations

- Unit: every validation rule pass and fail incl. boundaries (0, 1, 200, 201 chars; dates at bounds).
- Integration: persistence round trip.
- Contract: INVALID_ARGUMENT carries violations.
- Component: form pending, error, success.

## Definition of done

Apply `docs/backlog/definition-of-done.md` in full, plus the criteria above. No criterion is complete without command output as evidence.
