# S-102: List people with paging and sorting

**Epic:** E01 People management  
**Priority:** Must · **Size:** M · **Order:** 6 · **Wave:** 4  
**Status:** Draft (Phase 4)  
**Depends on:** S-101  
**Requirements:** FR-PPL-01, NFR-UX-03, NFR-PERF-01  
**BRD acceptance criteria owned:** AC-FR-PPL-01-1, AC-FR-PPL-02-1

## Objective

List people with paging and sorting.

## Acceptance criteria

- `AC-FR-PPL-01-1`: as defined in `docs/requirements/BRD.md` section 10.
- `AC-FR-PPL-02-1`: as defined in `docs/requirements/BRD.md` section 10.
- `S-102.AC1`: `PeopleService.ListPeople`, gateway `people` query and `/people` page with skeletons, empty state and pagination in the URL.
- `S-102.AC2`: Page beyond the last returns an empty page with correct totals and the UI moves to the last valid page (EC-11).
- `S-102.AC3`: Name sort toggle (asc/desc) with a secondary sort on id so equal names keep a stable order across pages.

## Business rules and edge cases

- size 1–100 (default 20); sort field allow-listed; paging invalid → `paging.invalid`.

## Test expectations

- Unit: paging maths (0 items, exact multiple, remainder).
- Integration: ordering is stable and case-insensitive.
- Component: skeleton, empty (EC-01), error, pagination.

## Definition of done

Apply `docs/backlog/definition-of-done.md` in full, plus the criteria above. No criterion is complete without command output as evidence.

## Why this design (for the walkthrough)

Lists drive most of the perceived-progress requirements (A-N3).
