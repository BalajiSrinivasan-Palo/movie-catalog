# S-304: Frontend artwork uploader with progress, cancel and retry

**Epic:** E03 Artwork  
**Priority:** Must · **Size:** M · **Order:** 18 · **Wave:** 8  
**Status:** Draft (Phase 4)  
**Depends on:** S-303, S-203, S-305  
**Requirements:** FR-ART-01, FR-ART-03, NFR-UX-02, NFR-A11Y-01  
**BRD acceptance criteria owned:** AC-FR-ART-01-1, AC-FR-ART-03-1, AC-FR-ART-03-2

## Objective

Frontend artwork uploader with progress, cancel and retry.

## Acceptance criteria

- `AC-FR-ART-01-1`: as defined in `docs/requirements/BRD.md` section 10.
- `AC-FR-ART-03-1`: as defined in `docs/requirements/BRD.md` section 10.
- `AC-FR-ART-03-2`: as defined in `docs/requirements/BRD.md` section 10.
- `S-304.AC1`: XHR helper reports percentage; ProgressBar has `role=progressbar` with values; at 100% a 'Processing…' state is shown until the response arrives.
- `S-304.AC2`: Cancel aborts the request and leaves previous artwork unchanged (EC-08); failure shows the specific message and a Retry action.
- `S-304.AC3`: Client-side pre-checks (type, size) give instant feedback but the server decision is final.
- `S-304.AC4`: Uploader is available on the create form (after the movie is saved) and on the detail page.
- `S-304.AC5`: If the movie is saved but the upload fails, the movie exists without artwork and the detail page offers Retry upload; cancel after 100% is best effort, so the UI re-fetches the movie to show the real state (EC-08).

## Business rules and edge cases

- Allowed: JPEG, PNG, WebP ≤ 5 MiB.

## Test expectations

- Unit: XHR helper with a fake XHR (progress, abort, error, timeout).
- Component: all uploader states, keyboard access.
- E2E (in S-603): real upload with visible progress.

## Definition of done

Apply `docs/backlog/definition-of-done.md` in full, plus the criteria above. No criterion is complete without command output as evidence.

## Why this design (for the walkthrough)

Progress reporting is called out by the assessment.
